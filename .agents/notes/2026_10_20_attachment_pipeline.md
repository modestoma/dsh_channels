# 附件管线 v2 的长期取舍（2026-10-20）

## 问题与适用范围

飞书渠道插件的入站附件（图片、文件、合并转发中的资源）如何进入会话：何时创建会话、何时下载字节、prompt 里放什么、文件存哪里、谁负责清理。适用范围是 `dsh-channels` 的私聊 / 对话群 / 话题群全部入站路径，以及后续新增渠道的同类实现。

## 备选方案

1. **现状：下载完再开模型回合**。附件在准入阶段同步落盘到话题 `attachments/`；纯附件消息不触发模型；引用、历史、合并转发内的资源覆盖差；大文件下载会占用话题处理队列。
2. **只做工具化**：立即建会话，模型按消息 id 调用工具下载。解决了阻塞，但没有规定 prompt 里放什么、图片如何进入模型、历史与引用如何发现。
3. **采纳方案：立即建会话 + 清单/摘录进 prompt + 图片预取 + 文件懒取 + DSH 原生附件库**。会话/话题/卡片零等待；prompt 用结构化清单声明“附件未加载”；触发消息的图片预取为原生 `ImageBlock`；文件在模型真正需要时由工具流式写入 `ctx.attachments`；引用消息、话题历史由消息工具按需读取。
4. **存储子方案**：
   - 文件落话题 `attachments/`：可清理、可写、工作区可见，但清理会破坏 Session 记录中的引用；
   - 图片与文件都走 DSH 原生附件库：不可变、内容寻址去重、读取时校验、永不自动删除；文件是只读副本，修改前需复制到工作区。

## 用户选择与理由

- 采用方案 3（本会话 2026-10-20 确认）。
- **仅附件消息**：静默登记元数据，不下载、不回复、不建会话；后续消息的 prompt 清单可引用它。
- **引用机器人消息但未 @**：对话群主聊天区不响应——飞书点击回复时默认 @ 被回复消息的发送方，手动删除 @ 即表达不需要机器人回复；已绑定话题 / 话题群内保持“话题内无需 @ 续聊”的既有规则。
- **模型漏调工具**：优化工具描述、prompt 清单（明确标注“未加载”）和测试用例收敛；**不接受预下载兜底**。
- **大文件**：懒取 + 单次资源数/字节上限 + 超时/取消；不做后台预取。
- **存储**：图片与文件都进 DSH 原生附件库；用户接受磁盘无自动回收。插件不再承担入站附件清理；工作区清理只保留给 Agent 产物与旧版目录。
- **借用 live agent**：用户认为无此需求；实现仍保留低成本工具补挂，作为宿主重启 / Web UI 打开同一会话竞态的防护。
- **理由**：Session 记录可回放且不可变；清理不再破坏历史；相同字节去重；图片原生可见；引用与历史只有按需工具能覆盖。
